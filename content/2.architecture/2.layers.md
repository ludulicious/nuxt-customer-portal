A feature layer is the unit of extension in Customer Portal. It packages one business capability and depends on portal core instead of reaching into the host application.

## Recommended structure

```text
layers/<feature>/
├── nuxt.config.ts
├── package.json
├── README.md
├── app/
│   ├── components/
│   ├── composables/
│   ├── pages/
│   └── plugins/<feature>-feature.ts
├── i18n/locales/
│   ├── en.json
│   └── nl.json
├── server/
│   ├── api/
│   ├── db/schema/
│   └── utils/
├── shared/
│   ├── feature.ts
│   └── types/
└── test/
```

Only add directories a feature needs, but keep ownership inside the layer.

## Dependency boundary

Feature code should use portal-core adapters:

- `usePortalSession()` for the current user and organization context;
- `usePortalFeatures()` for feature registration;
- `#portal/server/portal` for authenticated, tenant-aware server access;
- types under `#portal/shared/types` for feature definitions and policies.

Do not import host files with `~/` or `~~/`, and do not use private authentication or store implementations directly. The layer boundary is what makes a feature portable.

Drizzle schema files are the one practical exception to alias-only imports. Drizzle Kit reads those files outside Nuxt and does not resolve Nuxt aliases, so a schema may import the physical portal-core authentication schema solely to declare cross-schema foreign keys. Runtime code should still use the adapters above.

## Discovery and registration

Nuxt discovers local layers directly under `layers/` when they contain `nuxt.config.ts`. A feature plugin then registers its definition:

```ts [layers/example/app/plugins/example-feature.ts]
import { exampleFeature } from '../../shared/feature'

export default defineNuxtPlugin(() => {
  usePortalFeatures().registerFeature(exampleFeature)
})
```

Portal core merges the contribution into the application shell. A feature should never require a manual menu entry in the host.

## Enabling and disabling a layer

To enable a local feature, place it directly under `layers/` and restart Nuxt.

To disable it without deleting data, move it outside that directory and restart. Its pages, API routes, navigation, widgets, auto-imports, and translations disappear; its database objects remain.

For a packaged layer, add or remove the package from `extends` or `modules`, depending on how the package is distributed.

::note
Customer Portal does not yet publish a versioned feature-layer SDK or any built-in layer as a public package. The supported contribution path today is a source layer under `layers/`. Treat package distribution as an advanced, explicitly versioned integration until compatibility releases are available.
::

::warning
Code removal and data removal are separate operations. Dropping a feature’s PostgreSQL schema requires a deliberate, reviewed migration.
::

## Definition of done

A contributed layer should:

- build both when enabled and when excluded from a copy of the portal;
- keep English and Dutch locale keys aligned;
- reject unauthenticated, unauthorized, and cross-organization access;
- keep its tables and enums in its own PostgreSQL schema;
- avoid runtime imports from the host;
- pass tests, lint, type checking, and the production build.

Use the [layer creation guide](/contributing/create-a-layer) for an implementation sequence.
When the source layer works in a second portal checkout, continue with [Distribute a feature layer](/contributing/distribute-a-layer).
