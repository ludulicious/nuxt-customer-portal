Customer Portal ships five layers that establish the reusable platform before an optional business feature is added. They are composed from directories immediately below `layers/`; Nuxt discovers each directory containing a `nuxt.config.ts`.

These layers are not a hierarchy of increasingly specific base classes. Each owns a product boundary, while `portal-core` exposes the contracts that let the other layers and business features cooperate without private host imports.

## Layer catalog

| Layer | Owns | Primary routes | Server or data surface |
| --- | --- | --- | --- |
| `portal-core` | Application shell, session context, active organization, authorization adapters, feature registry, shared dashboard, notifications, and core identity schema | `/dashboard`, authenticated shell, API docs | Better Auth handler, permission endpoint, notifications, core Drizzle schema, feature-facing server adapters |
| `authentication` | Login, signup, email verification, and password recovery interfaces | `/login`, `/signup`, `/verify-email`, `/forgot-password` | Uses portal-core identity infrastructure; does not own a separate business schema |
| `account-organizations` | Profile, security, organization selection, invitations, organization settings, and organization email-provider credentials | `/my-organizations`, `/settings/**` | Profile and invitation handlers plus organization-scoped email-provider configuration |
| `administration` | Installation-wide organization and user administration | `/admin/organizations/**`, `/admin/users` | System-administrator organization, membership, invitation, user, role, and impersonation operations |
| `public-site` | Anonymous home, blog, contact, content, assets, and public navigation | `/`, `/blog/**`, `/contact` | Nuxt Content collections and public presentation; no business tenant schema |

The platform catalog describes source ownership, not deployment necessity. A branded deployment might replace `public-site`, while a normal authenticated portal still depends on `portal-core` and usually needs authentication and organization management.

## Portal core

`portal-core` is the stable integration boundary. It owns the shared layouts and session model, but it must not know which optional business features are installed.

Feature code consumes:

- `usePortalSession` for the current user, system role, active organization, and membership;
- `usePortalFeatures` and `registerPortalFeature` for navigation, modules, widgets, and policy contributions;
- `#portal/server/portal` for database, session, tenant, organization, and authorization adapters;
- portal-core identity tables when a feature needs a reviewed cross-schema foreign key.

Put behavior in portal core only when multiple unrelated layers require the same platform contract. A customer-specific workflow, domain repository, or feature menu belongs in a business layer.

[Open the pinned portal-core contracts](/reference/source-map#portal-core-contracts)

## Authentication

`authentication` owns the user interfaces for entering and recovering an account. Portal core owns the underlying Better Auth configuration, session handler, core identity schema, provider flags, and email infrastructure.

This separation means a contributor can change the login experience without moving identity tables or creating a second session abstraction. Registration behavior is controlled by `PORTAL_REGISTRATION_MODE`; provider visibility is controlled by the corresponding GitHub and Google flags.

Do not add organization membership or business onboarding to the authentication layer. After identity is established, organization concerns belong to `account-organizations` and feature-specific setup belongs to that feature.

[Configure registration and providers](/getting-started/usage#registration-and-administrators)

## Accounts and organizations

`account-organizations` owns the authenticated user's account and tenant-management experience. It contributes **My organizations** and **Settings** navigation, while its APIs handle profile updates, invitation acceptance and maintenance, and organization-owned email-provider credentials.

The layer does not grant installation-wide authority. Organization owners and administrators act inside the active organization; cross-installation user and organization management belongs to `administration`.

When adding an organization setting:

1. derive the active organization from the session;
2. distinguish owner-only secrets from ordinary administrator settings;
3. keep provider credentials server-side and return only safe status metadata;
4. add English and Dutch labels in the layer's locale files.

[Use accounts and organizations](/guides/account-and-organizations)

## Administration

`administration` contributes the **Admin** module only to the `admin` audience. It owns installation-wide organization and user views and the matching `/api/admin/**` handlers.

The layer can create and update organizations, manage memberships and invitations, change system roles, revoke sessions, and initiate impersonation. These are system-administrator operations, not an expanded version of an organization administrator's feature policy.

Business features should not import administration internals to obtain a bypass. Use the portal-core authorization adapters, which already apply the standard system-administrator behavior, and keep feature-specific actions typed in the feature policy.

[Administer the portal](/guides/system-administration)

## Public site

`public-site` owns the anonymous marketing surface included with the product application: home, blog, contact, content collections, components, translations, and public navigation contributions.

It is intentionally separate from the authenticated portal shell. A deployment can replace its brand and content or remove it in favor of an external marketing site without moving business APIs. Avoid placing authenticated dashboards or tenant data in this layer merely because a route is reachable from the home page.

[Customize and brand the portal](/getting-started/customization)

## Decide where a change belongs

Use this order when reviewing a proposal:

1. **Is it an optional business capability?** Create or extend a feature layer.
2. **Is it shared session, tenancy, authorization, registry, or shell behavior?** Consider portal core, with compatibility tests.
3. **Is it identity entry or recovery UI?** Use authentication.
4. **Is it the current user's profile or active-organization management?** Use accounts and organizations.
5. **Is it installation-wide user or organization administration?** Use administration.
6. **Is it anonymous marketing or editorial content?** Use the public site.

If the answer crosses two boundaries, define the smallest stable contract between the layers instead of importing a private component, composable, or repository across them.
