Customer Portal ships with the fictional **ApexPro** facilities brand as working reference content. It demonstrates a complete public site, but it is not a neutral production identity. Replace its claims, contact details, images, email branding, and metadata before exposing a derived portal publicly.

Start with a repository-wide inventory:

```bash [Terminal]
rg -n -i "apexpro|ludulicious|facility services|support@|sales@" \
  --glob '!node_modules/**' --glob '!.git/**'
```

Run the search again before release. A visual logo change alone does not remove the reference brand from page titles, email, API documentation, or localized content.

## Choose an application theme

The host currently defines two theme names:

| Theme | Purpose |
| --- | --- |
| `apex` | Nuxt UI's comparatively neutral base presentation |
| `brutal` | The stronger editorial treatment used by the reference deployment |

Select one and set the Nuxt UI colors in `app/app.config.ts`:

```ts [app/app.config.ts]
export default defineAppConfig({
  portal: {
    theme: 'apex'
  },
  ui: {
    colors: {
      primary: 'blue',
      neutral: 'slate'
    }
  }
})
```

The accepted names live in `app/themes/portal-theme.ts`. An unknown value falls back to `apex`. Add a new theme there only when the deployment needs a reusable set of component overrides and browser theme colors; use ordinary Nuxt UI configuration for smaller changes.

Test every theme in light and dark mode. Theme selection affects component styling and the browser `theme-color` metadata.

## Replace the global identity

Review these host and portal-core surfaces together:

| Surface | Current source |
| --- | --- |
| Page title suffix, social image, favicons | `app/app.vue` and `public/` |
| Header mark, wordmark, subtitle, and home link label | `layers/portal-core/app/components/AppHeader.vue` |
| Standalone logo component | `layers/portal-core/app/components/AppLogo.vue` |
| Footer owner and copyright | `layers/portal-core/app/components/AppFooter.vue` |
| OpenAPI title and description | root `nuxt.config.ts` |
| Authentication email brand | `runtimeConfig.portalEmail.brandName` |
| Authentication email header and footer | `layers/portal-core/server/utils/email-template.html` |

The header and standalone logo currently contain separate copies of the reference SVG and wordmark. Update both or refactor them to one shared component so they cannot drift.

Override the merged email brand from the host configuration:

```ts [Runtime configuration]
export default defineNuxtConfig({
  runtimeConfig: {
    portalEmail: {
      brandName: 'Example Company'
    }
  }
})
```

Also change the HTML email template: `brandName` controls OTP subjects, while the template owns its visible header, destination, and copyright. Send verification, sign-in, password-reset, invitation, and account-deletion messages to a controlled mailbox before release.

## Rewrite the public site

The `public-site` layer owns `/`, `/contact`, and `/blog`.

Edit both locales:

```text
layers/public-site/
├── content/en/0.index.yml
├── content/nl/0.index.yml
├── content/en/2.blog.yml
├── content/nl/2.blog.yml
├── content/en/blog/
├── content/nl/blog/
└── i18n/locales/{en,nl}.json
```

The reference homepage mentions facilities orders, SLA monitoring, attachments, and notifications. Do not leave those claims in a deployment unless its installed layers actually provide them. Marketing copy should match the enabled feature set and link to real routes.

Replace the hero image at `layers/public-site/public/images/home/office.png` and review its alt text in the public homepage component. The contact page also contains hard-coded sales and support addresses plus a social link; change those in `layers/public-site/app/pages/contact.vue` as well as its translated labels.

::note
The current blog index reads the English content collections directly. If the deployment requires a localized blog, make the collection selection follow the active locale and verify both indexes and every post route.
::

If a deployment does not need a public marketing surface, remove the `public-site` layer and provide a replacement public route or redirect for `/`. Removing the layer does not affect authentication or authenticated business modules.

## Validate the branded build

Before deployment:

1. repeat the reference-brand search and review every remaining match;
2. inspect `/`, `/contact`, `/blog`, authentication pages, the dashboard, and `/api-docs`;
3. check the header, footer, organization switcher, favicon, page title, and social preview;
4. render English and Dutch in light, dark, desktop, and narrow layouts;
5. send every platform email flow and an organization invoice email;
6. confirm public copy describes only installed, tested capabilities;
7. run feature tests, lint, typecheck, and the production build.

Brand changes should remain in the thin host or the public-site layer. Keep business feature layers portable and free of deployment-specific names unless the feature itself owns that identity.
