Deploy the same SaaS portal application using either a source build or the published Docker image. Use PostgreSQL 16, HTTPS in production, unique secrets and persistent file storage. PUBLIC_URL and BETTER_AUTH_URL must match the public origin exactly. Local URLs use localhost.

## Docker deployment

Use compose.yaml and .env.example from the repository. Set PORTAL_IMAGE to a verified release tag or immutable digest, POSTGRES_PASSWORD to a URL-safe secret, BETTER_AUTH_SECRET to a separate long secret, PORTAL_ENCRYPTION_KEY to a base64-encoded 32-byte key, and ADMIN_EMAILS to your reserved administrator email. Set PUBLIC_URL to your HTTPS origin.

```sh
docker compose up -d
docker compose logs portal
```

The entrypoint checks configuration, reports migration status, applies migrations, and bootstraps a provider when its name and slug are configured. A failed migration prevents startup. PostgreSQL and local file storage use named volumes. Back up both; see [backup and restore](/operations/backup-and-restore). Configure your reverse proxy to forward the public host and HTTPS headers.

Use the hosting platform's secret facilities for email, OAuth, payment, and calendar credentials. The example Compose file is a baseline; pass additional documented variables to the portal service as needed. Never bake secrets into an image.

## Source deployment

From the repository root:

```sh
pnpm install --frozen-lockfile
pnpm build
pnpm db:status
pnpm db:migrate
node --env-file=apps/saas-portal/.env apps/saas-portal/.output/server/index.mjs
```

Operational commands load apps/saas-portal/.env. The built server does not automatically load it; the example uses --env-file explicitly. Inject production variables through your process supervisor instead when available. Keep the process working directory consistent with local file-storage configuration.

## Release and upgrade sequence

1. Back up the database and file storage, and verify the restore procedure.
2. Read CHANGELOG.md and review pending SQL from the exact version to deploy.
3. Build and verify that revision, or select its verified Docker image/digest.
4. Apply migrations before directing traffic to the new revision. Docker startup does this automatically.
5. Verify sign-in, organization scope, module navigation and changed business workflows.
6. Inspect logs and external-provider status.

Use backward-compatible migrations when old and new replicas overlap. GitHub releases publish the Docker image only after the complete source verification workflow succeeds. A source release, product version and image version identify the same product; private modules have no independent release cycle.

For deployment failures, follow [upgrade recovery](/operations/upgrade-recovery). For synthetic public demonstrations, use the same image with the [dedicated demo configuration](https://github.com/ludulicious/nuxt-customer-portal/blob/master/apps/saas-portal/layers/demo/README.md); never enable demo mode on a real database.
