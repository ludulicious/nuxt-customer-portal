The `products` layer, published as `@nuxt-customer-portal/products`, provides one provider-owned store with localized products, categories, prices, checkout, purchase history, and protected files. Products may be free or paid, digital or service-based, and published only after their required content, media, prices, and files are complete.

## Store setup

Administrators configure the store under `/admin/products/settings`:

- **General settings** control whether the store is open, sandbox or live mode, languages, currencies, tax behavior, and image requirements.
- **Styles** control the storefront and Markdown presentation.
- **Stripe** stores organization-specific credentials only when Stripe is not supplied by the deployment environment.
- **Storage** configures local-compatible S3 or Bunny storage for product images and purchased files.

New stores start in sandbox mode. Sandbox checkout tests successful, failed, and expired payments without Stripe. Switch to live mode only after Stripe, webhook delivery, storage, email, tax, and invoice settings have been verified.

## Catalog and purchases

Product administration supports localized content, stable category assignments, multi-currency prices, image-purpose crops, downloadable files, publish checks, and previews. The public store exposes published products and creates immutable order snapshots so later catalog edits do not rewrite purchases.

Clients see their purchases under `/purchases`. Purchase details open in a drawer with the order reference, price, date, invoice action, next steps, and downloadable files. Anonymous checkout creates or links a private client by verified email and can invite that customer into the portal.

## Stripe and delivery

Paid checkout uses Stripe Checkout and the signed webhook at `/api/store/webhooks/stripe`. Configure the webhook for the payment and checkout events listed in Store settings. Processing is idempotent: repeated events reuse the order, payment, delivery, email, and integration records.

Digital delivery requires configured storage. Free products use the normal purchase-confirmation and delivery flow without Stripe or an invoice.

## Invoice integration

Install the `invoice-products` layer, published as `@nuxt-customer-portal/invoice-products`, with Products and Invoices. A completed paid order creates one sales invoice from its immutable lines and payment. Refunds create linked credit notes without rewriting the original invoice. Complete the invoice sender, numbering, tax, and transactional email configuration before opening the live store.

## Composition

```ts [portal.config.ts]
layers: [
  '@nuxt-customer-portal/preset',
  '@nuxt-customer-portal/invoices',
  '@nuxt-customer-portal/products',
  '@nuxt-customer-portal/invoice-products'
]
```

Add [Planning](/modules/planning) after Products when services need bookable appointments.

## Scheduled offers

Store administrators can add, edit, and cancel multiple offers in a product's pricing section. Each offer has an exact start and end time, shown in the administrator's browser timezone and stored in UTC. The start is included; the end is excluded. Overlapping offers and ambiguous daylight-saving times are rejected. Set a reduced amount in every configured currency, or choose a free offer. Regular prices resume automatically after the end.

The store catalog list, detail, and storefront APIs resolve prices at request time without caching. Each `prices[]` item retains its effective `id`, `currency`, `amount`, and `taxBehavior`, and adds `originalAmount` (the regular price) and `offer` (`{ id, startsAt, endsAt }` while active, otherwise `null`). Without an offer, `originalAmount` equals `amount`. Amounts use currency minor units; a free offer returns zero. `isFree` reflects effective pricing. Currency filters apply to active offers.

Offer management uses the existing store-admin authorization: `POST /api/products/admin/products/:id/offers`, `PUT /api/products/admin/products/:id/offers/:offerId`, and `DELETE /api/products/admin/products/:id/offers/:offerId`. Create/update bodies contain `startsAt` and `endsAt` as ISO timestamps with offsets, `isFree`, and `prices` (currency, amount, taxBehavior; empty for free offers). Store tax settings determine the applied tax behavior. Admin product reads include `offers` separately from regular `prices`. Cancellation retains historical offers and order references. Ended offers are read-only.

Checkout rechecks the price and rejects stale price IDs with a refresh-required conflict. Service reservations do not lock offer prices; a changed quote requires a new reservation. Created orders and checkout retries retain their agreed price. Regular-price or store-currency changes that invalidate active or future offers are rejected until those offers are updated or cancelled. Existing appointment-change fees are unaffected.

## Purchased-file delivery

Apply the products migrations when upgrading. Each order has a permanent, unguessable purchase token. Paid orders (including free purchases) expose only the ready files in their purchase snapshot. Links require no portal account and recheck payment, refunds, and disputes on every request. Anyone holding a link can use it; keep purchase tokens out of analytics, logs, and public caches.

Confirmation emails include a localized list of file links using the `{{downloads}}` placeholder. If you customized the purchase email body, add this placeholder to your override. Existing purchases also receive tokens during migration; already-sent emails are not resent.

The `downloads` placeholder contains the file links only. Add a conditional section to customize the introduction, and leave it out entirely when no files are available:

```text
{{#if downloads}}
You can download your audio files here:

{{downloads}}
{{/if}}
```

In **Admin → Email → Email texts**, use Source view to edit the tags. The preview/test switch lets you check the same email without downloads. An optional `{{else}}` before `{{/if}}` supplies alternative text. Conditions work with any placeholder declared for that email; empty or whitespace-only values select the alternative. Conditions are evaluated before Markdown formatting, and nested sections are supported. Invalid, unclosed, or unknown conditions are rejected when saving or previewing. The global HTML email template supports the same syntax with its own placeholders.

Successful checkout URLs include a `purchase` token on the portal payment-result page. That page displays the files and passes the token to the configured `returnUrl` when the buyer follows its return action. To use a calling website's thank-you page, supply that page as checkout `returnUrl` (or configure it as the store return URL). No calling website is modified by installing the portal update.

The calling thank-you page can fetch the file list without portal login or a catalog API key:

```js
const token = new URL(location.href).searchParams.get('purchase')
if (token) {
  const response = await fetch(`https://portal.example.com/api/store/purchases/${encodeURIComponent(token)}`)
  if (response.ok) {
    const { status, files } = await response.json()
    // Render files as links using file.name and file.url.
    // If status is pending, retry after a few seconds while payment is confirmed.
  }
}
```

The response contains only `{ status, files: [{ id, name, url }] }`, without billing or customer information. Browser access is allowed from the origin of the order's original `returnUrl`; server-side retrieval also works. Use `Referrer-Policy: no-referrer` on the calling thank-you page and exclude its `purchase` query parameter from analytics. Never treat the token or a success URL as proof of payment: use the returned file list, which remains empty until payment is confirmed.

Each file URL is a stable `/api/store/purchases/:token/files/:assetId` permalink. The portal resolves it to current storage delivery, so temporary S3 URLs can expire without breaking the permalink. Successful GET requests that initiate an attachment response or storage redirect create a `products.download` row with the order, order line, asset, source (`public` or `portal`), and timestamp. Previews and HEAD requests do not count. These records indicate delivery requests, not verified completion of the browser's file transfer. Storage failures before delivery do not count.
