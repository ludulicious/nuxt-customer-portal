Module composition lives in apps/saas-portal/portal.config.ts. The main application's Nuxt configuration extends those sources and its integrated demo layer. The module list explicitly includes core, UI, authentication, organizations, administration and clients; there is no preset or kit.

```ts
import { definePortalConfig, localPortalLayer } from '@nuxt-customer-portal/core/config'

export default definePortalConfig({
  layers: [
    '@nuxt-customer-portal/core',
    '@nuxt-customer-portal/ui',
    // Keep the existing platform and business modules here.
    localPortalLayer({
      id: 'notes',
      source: './layers/notes',
      migrations: './migrations',
      dependsOn: ['core']
    })
  ]
})
```

This is an extension excerpt, not a replacement for the complete application configuration. Local provider metadata and migration paths are resolved relative to the declared layer root; Nuxt layer paths are relative to the host. Keep module dependencies explicit.

Each workspace module exports nuxt.config.ts and, when it provides migrations, portal.manifest.mjs. The manifest declares its id, dependencies, schema and migration location. The repository operation orders dependencies and checks migration checksums. Product release versions come from the root package.json.

Use [Create a feature layer](/contributing/create-a-layer) to add routes, navigation, API handlers and migrations. Keep optional modules independent and import shared contracts through workspace exports.
