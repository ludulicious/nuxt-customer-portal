Customer Portal separates database ownership by PostgreSQL schema while keeping migration ordering at the application root. This lets a feature own its records without making deployment order ambiguous.

## What Drizzle discovers

The root `drizzle.config.ts` includes:

```ts [drizzle.config.ts]
schema: [
  './layers/portal-core/server/db/schema/**/*.ts',
  './layers/*/server/db/schema/**/*.ts'
]
```

Portal-core and authentication objects remain in `public`. A business layer declares its own namespace with `pgSchema`, using the layer name with hyphens replaced by underscores.

## Generate a change

Change the Drizzle schema in the owning layer, then generate from the repository root:

```bash [Terminal]
pnpm exec drizzle-kit generate --name=describe-the-change
```

Commit both the schema source and generated migration. Do not maintain a second migration journal inside the layer: the root `drizzle/` directory is the deployment history for the assembled application.

## Review the SQL

Generated SQL is a starting point, not an approval. Check:

- whether a detected drop should be a rename;
- whether existing rows satisfy new non-null columns and constraints;
- whether backfills happen before constraints depend on them;
- whether foreign-key deletion behavior matches the domain;
- whether indexes support new tenant-scoped queries;
- whether long-running statements need a staged release.

For data that already exists, prefer an expand-and-contract sequence: add compatible structures, backfill, switch application reads and writes, then remove obsolete structures in a later release.

## Apply and verify

Use a disposable PostgreSQL database before production:

```bash [Terminal]
pnpm exec drizzle-kit migrate
pnpm test:features
pnpm typecheck
pnpm build
```

Test both a fresh database and an upgrade from representative existing data when the change transforms records. Exercise the affected workflow, authorization boundaries, and organization scoping after migration.

Before production, verify a restorable backup and decide whether the change permits an application-only rollback or requires a forward repair. The [upgrade recovery runbook](/operations/upgrade-recovery) covers partial migrations and post-release regressions.

## Removing a layer

Disabling or moving a feature layer removes its runtime contributions but intentionally leaves its schema and data intact. Data removal requires a separate reviewed migration and an explicit retention decision.

This separation makes disabling code reversible. Never make a feature’s absence automatically drop production data.
