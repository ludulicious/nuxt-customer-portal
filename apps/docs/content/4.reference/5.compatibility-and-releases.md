The root package.json contains the product version. GitHub source releases and Docker tags use that version. Modules under packages/ are private workspaces released with the app; there is no independent module-version matrix, npm publication or generated installer.

## Supported installation and tooling

Clone the repository or run the Docker image. Source development uses Node.js 22.19 or newer on a supported Nuxt-compatible LTS release and pnpm 10.30.2. The pinned pnpm version is shared by CI and Docker. Other package managers require a fork and are outside project support.

## Prepare a release

1. Collect changes in the root CHANGELOG.md under Unreleased. Include upgrade notes and migration impact.
2. Set the root product version for the release and move the notes to that version's section.
3. Verify source tests, formatting, types, builds, demo/reset checks and portal browser tests.
4. Merge the preparation PR, then publish the GitHub release against its reviewed commit.
5. Full source verification must pass before the Docker publisher runs. Record the image digest and source commit before announcing availability.

Only the root product version is authoritative. Migration journals retain their existing package_version column for database compatibility; new entries record the product version. Applied migration names and checksums remain immutable.

## Upgrades

Back up data and files before changing revisions. Source users update their checkout, install with the committed pnpm lockfile, build and apply migrations. Docker users select the new verified image and let its entrypoint apply migrations. Read [upgrade recovery](/operations/upgrade-recovery). Old installation URLs lead to source/manual setup documentation rather than an unsupported package workflow.
