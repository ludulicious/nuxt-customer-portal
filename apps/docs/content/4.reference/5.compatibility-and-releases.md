Customer Portal is currently an application template under active development. The host package is version `0.0.0`, the portal-core layer is private to the application, and the repository does not yet publish tagged releases. There is therefore no SemVer compatibility promise for `master` today.

::warning
The Customer Portal product repository is public, but the revision verified by this documentation does not contain an explicit software license. The project is intended for an open-source release; until maintainers adopt that license, do not treat public source access as permission to use, modify, or redistribute the product. See [GitHub's repository licensing guidance](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/licensing-a-repository).
::

## What is stable today

The architecture deliberately concentrates feature integration in a small set of portal-core contracts:

- `PortalFeatureDefinition` for shell contributions;
- `PortalFeaturePolicy` and the server authorization adapters;
- `usePortalSession()` and `usePortalFeatures()` for feature UI;
- `#portal/server/portal` for authenticated tenant context;
- the root PostgreSQL migration history for assembled deployments.

These are the intended extension points, but a commit on `master` may still change them. Internal file paths, raw database records, host components, and feature implementation utilities are not compatibility surfaces.

## Pin production deployments

Record the exact source commit used by every deployment:

```bash [Terminal]
git rev-parse HEAD
```

Do not automate production deployments directly from a moving `master` branch. Use a deployment branch, immutable commit, or organization-owned tag after the change has passed that deployment's migration and workflow checks.

For an external feature layer, record both:

- the Customer Portal commit it was tested against;
- the layer commit or package version.

## Upgrade procedure

Treat every upstream update as an integration change:

1. read the source diff from the pinned commit to the target commit;
2. inspect portal-core contracts and feature aliases for changes;
3. review every new migration and dependency change;
4. apply migrations to an empty database and a representative copy of existing data;
5. run feature tests, locale validation, lint, typecheck, and build;
6. exercise authentication, organization switching, authorization, and the deployment's critical business workflows;
7. compare `/api-docs/openapi.json` if another system consumes the API;
8. deploy with a database backup and a rollback plan.

Database rollback may require a forward repair migration. Reverting application code does not automatically undo an already-applied schema migration.

Operators should rehearse [backup and restore](/operations/backup-and-restore) and use the [upgrade recovery runbook](/operations/upgrade-recovery) rather than improvising against the production migration journal.

## Breaking changes

Until tagged releases begin, a change is breaking when it requires a deployment or external layer to change any of the following:

- a portal-core type, composable, alias, or server adapter;
- a migration ordering or schema assumption;
- an environment variable or its meaning;
- an authenticated API route or response used outside its owning UI;
- a translation namespace consumed across layers.

Pull requests with such a change should state the affected consumers, include an upgrade path, update this documentation in the same change, and avoid mixing unrelated behavior.

## Before the first stable release

A tagged release process should not be implied until the repository has, at minimum:

- an explicit open-source license;
- public contributor and security policies;
- an agreed versioning scheme and changelog;
- repeatable release tags and release notes;
- a compatibility statement for portal-core extension points;
- tested install and upgrade paths.

Until those conditions are met, the accurate public label is **public source under active development, with licensing pending**. Production use is possible in authorized deployments—as demonstrated by the timesheets and invoices module—but each deployment owns its authorization, pinning, testing, and upgrade decision.
