Nuxt Customer Portal is an MIT-licensed monorepo. Copyright belongs to “Nuxt Customer Portal contributors”; the repository root `LICENSE` governs the reusable packages and source unless a file says otherwise.

Public package versions and changelogs are managed with Changesets. Starting with `0.3.0`, releases use ordinary version numbers without an alpha suffix. Before `1.0.0`, minor releases may introduce documented breaking changes; patch releases preserve compatibility. Review each package's changelog before upgrading and keep all official packages on the same version.

## Adoption and release status

All 16 official packages are published on npm with linked versions. The [installation guide](/getting-started/installation) uses the [`latest` release of the portal kit](https://www.npmjs.com/package/@nuxt-customer-portal/kit) to create a standalone application, so its commands do not need to change for each release.

Timesheets and invoicing are used by the maintainers' software agency. Version `0.3.0` is the first npm release. Use `0.3.1` or newer when creating a portal on Node 24; it fixes template copying during setup. Evaluate compatibility with your host, deployment, and custom modules before upgrading. Service Requests is an optional example extension for developers.

## Release 0.8.0

Version 0.8.4 adds account-free order links, purchased external links and media previews, and Store texts for shared page wording and product-specific purchase introductions. Apply Products migrations `0022_page_texts.sql` and `0023_product_page_texts.sql` before deploying. Existing thank-you customizations and purchase snapshots are preserved. All official npm packages and the portal Docker image use version `0.8.4`.

Version 0.8.0 adds deferred invoicing with immediate fulfillment, unlisted products with unguessable slugs, protected purchase-file links, conditional email text, and a shared release verification gate. Apply Products migrations `0019_purchase_downloads.sql` and `0020_deferred_payments.sql`, and Invoices migration `0004_deferred_invoice_review.sql`, before deploying. Existing stores retain online payments and listed products. Deferred checkout requires tax-inclusive prices and the invoice integration; review each draft's taxes before sending.

## Supported baseline

- Nuxt 4 and compatible Vue/framework peers;
- PostgreSQL;
- English and Dutch;
- npm, pnpm, Yarn, and Bun consumers.

Documented package exports are the compatibility surface. Host aliases, physical paths across packages, demo shell components, raw internal records, and direct changes to official database tables are not.

## Upgrading

1. Read package Changesets and compare manifests.
2. Run `nuxt-customer-portal doctor`.
3. Inspect `nuxt-customer-portal db status` and the pending SQL.
4. Test a fresh database and an upgrade copy.
5. Run typecheck, builds, package tests, and critical portal workflows.
6. Deploy with a restorable backup and a forward-repair plan.

Checksums make published migration files immutable. Disabling a package leaves its data intact. A host that alters an official table must fork or explicitly take over that provider's migration stream and cannot assume upstream compatibility.

## Publishing

Pull requests run lightweight checks: package tests, formatting/lint, the SaaS boundary check, and the primary portal type check. All pnpm, npm, Yarn, and Bun consumer checks run only during full verification. Documentation tests run only for relevant changes. Full builds, browser tests, package-manager compatibility, starter compatibility, and Docker validation run before release instead of on every PR or merge.

Publishing a GitHub release starts **Release packages and portal image** (`release-npm-packages.yml`). It resolves the release tag to an exact commit, checks that public package versions match, and runs **Full release verification** once. Both npm and portal Docker publication wait for all verification jobs to pass and publish from the verified commit. A failed or cancelled check prevents both publishers from starting. The portal image's SHA tag, revision label, and deployment reference identify that commit, including manual release retries.

To run the complete suite without publishing, manually start **Full release verification** and provide a branch, tag, or commit. To retry publication, manually start **Release packages and portal image** with the existing stable `release_tag` (for example `v1.2.3`). The Docker workflow has no separate release or manual publication trigger. Existing releases whose tag predates this workflow split can be retried from the updated default-branch workflow. npm authentication uses trusted publishing and GitHub's short-lived OIDC identity; the release workflow does not require a long-lived npm token.

The first publication of a new package requires an authenticated npm account with permission to publish to the `@nuxt-customer-portal` scope. npm requires the package to exist before a trusted publisher can be configured. After the initial publication, configure `release-npm-packages.yml` as the trusted GitHub Actions publisher for each package, with owner `ludulicious` and repository `nuxt-customer-portal`. See the [npm trusted-publisher prerequisites](https://docs.npmjs.com/cli/v11/commands/npm-trust/#prerequisites). A release does not change DNS, migrate production databases, or modify Ludulicious.

Maintainers should follow the [documentation release checklist](https://github.com/ludulicious/nuxt-customer-portal/blob/master/apps/docs/README.md#release-checklist): prepare docs first, verify locally packed packages, publish npm packages, verify a clean registry installation, and then deploy the matching documentation.
