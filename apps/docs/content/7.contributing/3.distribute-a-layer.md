A reusable layer is more than a directory that works in its author’s checkout. A consumer needs a supported installation shape, explicit compatibility, reversible migrations, and enough documentation to operate the feature without reading its source.

::warning
Customer Portal does not yet publish a versioned layer SDK or any built-in feature layer as a public package. The most reliable contribution today is an in-tree source layer reviewed against the exact Customer Portal revision that will ship it. Git and npm distribution are possible through Nuxt, but the layer author owns compatibility until Customer Portal begins publishing stable releases.
::

## Choose the contribution shape

| Shape | Use it when | Consumer action | Current support |
| --- | --- | --- | --- |
| Upstream in-tree layer | The feature should ship in the default Customer Portal template | Merge the layer and migration into Customer Portal | Preferred for core community contributions |
| External source layer | One or several deployments share a feature outside the default template | Place or synchronize the source below `layers/` | Supported by the current architecture |
| Git-extended Nuxt layer | Consumers need a pinned remote source without vendoring it | Add a tagged Git source to `extends` | Nuxt-supported; Customer Portal compatibility is author-managed |
| npm Nuxt layer | The feature has its own releases, dependencies, and maintenance lifecycle | Install the package and add it to `extends` | Nuxt-supported; no Customer Portal package ABI yet |

Start in-tree even if you eventually intend to publish. Auto-scanned source layers expose dependency mistakes early and participate in the root migration and test workflows.

## Make the source layer portable

Before copying it to another checkout, remove assumptions that only hold in the original host:

- import runtime portal services through `#portal`;
- use relative imports or a deliberate named-layer alias for the layer’s own files;
- never import application code through `~/` or `~~/`;
- own translations, routes, components, API handlers, types, tests, and database objects;
- accept secrets and public settings through documented runtime configuration;
- avoid deployment names, customer names, fixed organization IDs, and absolute filesystem paths;
- keep optional providers behind configuration and give disabled states useful errors;
- verify the portal still builds when the layer is removed.

Drizzle schema files may physically import the portal-core authentication schema to declare foreign keys because Drizzle Kit does not resolve Nuxt aliases. That exception does not apply to runtime code.

## Write the layer contract

Add a `README.md` at the layer root before asking another person to install it. It should answer:

1. What user problem does the layer solve?
2. Which Customer Portal revision or release range was tested?
3. Which routes, modules, navigation, widgets, roles, and actions does it add?
4. Which environment variables and external services are required?
5. Which PostgreSQL schema and migrations does it own?
6. How is it enabled, disabled, upgraded, and permanently removed?
7. Which commands prove a supported installation?
8. Where are bugs, security reports, and compatibility problems reported?

Include a small compatibility table and update it from actual test results:

```markdown
| Layer version | Customer Portal revision | Node | PostgreSQL | Status |
| --- | --- | --- | --- | --- |
| 0.1.0 | 96bcf57 | current LTS | project baseline | verified |
```

Do not write `latest` as a compatibility promise. A commit, tag, or release range makes a failed installation diagnosable.

## Contribute an in-tree layer

For a layer intended to ship with Customer Portal:

1. Agree on the boundary in a [module proposal](/contributing/propose-a-module).
2. Add the source below `layers/<feature>`.
3. Add its schema changes to the root Drizzle migration history.
4. Add the layer to the locale-parity and boundary tests when those tests enumerate layers.
5. Document both the contributor-facing contract and the user workflows.
6. Prove the enabled and excluded builds.
7. Keep the first pull request focused enough to review authorization and data ownership carefully.

The host should not gain feature-specific imports, navigation entries, or dashboard conditionals. If the layer reveals a genuinely reusable missing contract, propose the smallest portal-core addition separately and show at least two consumers.

## Share an external source layer

The simplest external distribution is a repository whose root is the layer itself. Consumers can vendor a tagged copy into `layers/<feature>` or synchronize it with their chosen Git workflow. Once it is under `layers/`, no `extends` entry is required.

Pin the imported source. Record the upstream repository and revision in the consuming project, and review changes before updating. Code updates and database migrations should travel together, but applying a migration must remain an explicit deployment step.

Do not make uninstalling the source automatically drop its PostgreSQL schema. Disable code first, verify the portal without it, preserve or export required records, and use a separate reviewed removal migration only when the data is no longer needed.

## Extend a Git-hosted layer

Nuxt can consume a remote Git layer through `extends`. Pin a release tag or immutable commit rather than a moving branch:

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  extends: [
    ['github:example/customer-portal-notes#v0.1.0', {
      meta: { name: 'notes' }
    }]
  ]
})
```

If the remote layer has dependencies that Nuxt must install, the corresponding Nuxt layer option can use `install: true`. Private sources require consumer-managed credentials. Consult the [current Nuxt layer documentation](https://nuxt.com/docs/4.x/getting-started/layers) before publishing because remote-layer resolution and installation behavior belong to Nuxt, not Customer Portal.

Test the exact remote form in a clean checkout. A local directory can accidentally resolve workspace dependencies or aliases that are unavailable after Nuxt downloads it.

## Publish an npm layer

Only choose npm when someone will maintain releases and dependency updates. The package entry point is the layer’s `nuxt.config.ts`:

```json [package.json]
{
  "name": "@example/customer-portal-notes",
  "version": "0.1.0",
  "type": "module",
  "main": "./nuxt.config.ts",
  "files": [
    "app",
    "i18n",
    "server",
    "shared",
    "nuxt.config.ts",
    "README.md"
  ],
  "peerDependencies": {
    "@nuxtjs/i18n": "^10.6.0",
    "drizzle-orm": "^0.45.2",
    "nuxt": "^4.5.1"
  }
}
```

Give a distributed layer a stable named alias:

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  $meta: { name: 'notes' },
  modules: ['@nuxtjs/i18n']
})
```

After publishing, the consumer installs the package and extends it:

```bash [Terminal]
pnpm add -D @example/customer-portal-notes@0.1.0
```

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  extends: ['@example/customer-portal-notes']
})
```

Dependencies imported at runtime must be declared by the package. Development-only test and build tools remain development dependencies. Verify the packed archive before publication so source, translations, server routes, and schemas are actually present.

::note
An npm or Git layer does not automatically join the consuming application’s Drizzle schema glob or migration history. Provide reviewed SQL or a documented schema integration step, and require consumers to incorporate it into their own ordered migration workflow. This is one reason in-tree contributions remain the safest path today.
::

## Version migrations with code

Treat schema compatibility as part of the layer release:

- make forward migrations safe for existing data;
- never reuse or silently rewrite a published migration;
- document required backup and rollout order;
- distinguish disabling code from deleting data;
- test upgrades from every supported prior layer version;
- include rollback or recovery instructions when a code rollback cannot reverse the schema change.

When Customer Portal itself has no stable release covering the required contract, pin the exact tested commit. Update that pin only after repeating the clean-checkout, migration, authorization, type, and build checks.

## Release checklist

- The layer passes the full [testing contribution checklist](/contributing/testing).
- A clean Customer Portal checkout builds with the distributed form installed.
- The same checkout builds after the layer is disabled.
- The README states exact compatibility and configuration.
- The package or Git tag contains every required source and locale file.
- Installation and upgrade migrations succeed on a disposable database.
- Unauthenticated, unauthorized, and cross-organization requests are rejected.
- The install, upgrade, disable, and data-removal paths are documented separately.
- User documentation exists for every contributed workflow.
- Issue and security-reporting channels are reachable.

The distribution mechanism does not make a feature reusable by itself. Portability is proven when another person can install the pinned artifact in a clean portal, migrate safely, complete the documented workflow, remove the code without breaking the host, and understand what happens to the data.
