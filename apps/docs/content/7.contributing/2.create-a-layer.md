This tutorial takes a small `notes` capability from an empty directory to a working source layer. It uses the same boundaries as the production service-request and timesheets layers: the host discovers the code, portal core supplies stable contracts, and the feature owns its routes, policy, data, translations, and tests.

## Before you start

Work from a current Customer Portal checkout with its dependencies installed. Run the existing suite once so later failures are attributable to the new layer:

```bash [Terminal]
pnpm test:features
pnpm typecheck
```

Define the boundary before creating files. For this example, notes belong to one active organization, authenticated members may read and create them, and organization administrators may also manage them. The feature does not change a host page or accept an organization selector from the browser.

## 1. Create the source layer

```text
layers/notes/
├── README.md
├── nuxt.config.ts
├── app/
│   ├── pages/notes/index.vue
│   └── plugins/notes-feature.ts
├── i18n/locales/
│   ├── en.json
│   └── nl.json
├── server/
│   ├── api/notes/index.get.ts
│   └── db/schema/notes.ts
├── shared/feature.ts
└── test/notes.test.ts
```

Nuxt automatically discovers a directory immediately below `layers/` when it contains `nuxt.config.ts`. Restart the development server after creating or moving a layer.

The layer configuration enables its locale files:

```ts [layers/notes/nuxt.config.ts]
export default defineNuxtConfig({
  compatibilityDate: '2025-10-24',
  modules: ['@nuxtjs/i18n'],
  i18n: {
    locales: [
      { code: 'en', iso: 'en-US', name: 'English', file: 'en.json' },
      { code: 'nl', iso: 'nl-NL', name: 'Nederlands', file: 'nl.json' }
    ]
  }
})
```

An in-tree source layer does not need its own `package.json`. Add one only when you need package metadata or deliberately start a separately versioned distribution.

## 2. Define the feature contract

The shared definition is serializable metadata. It declares what the shell may show and what each organization role may do:

```ts [layers/notes/shared/feature.ts]
import type { PortalFeatureDefinition } from '#portal/shared/types/feature'

export const noteActions = ['read', 'create', 'manage'] as const
export type NoteAction = typeof noteActions[number]

export const notesFeature: PortalFeatureDefinition<NoteAction> = {
  id: 'notes',
  navigation: [{
    id: 'notes',
    labelKey: 'features.notes.title',
    icon: 'i-lucide-notebook-tabs',
    to: '/notes',
    audiences: ['authenticated'],
    order: 40
  }],
  modules: [{
    id: 'notes',
    labelKey: 'features.notes.title',
    icon: 'i-lucide-notebook-tabs',
    to: '/notes',
    routePrefixes: ['/notes'],
    audiences: ['authenticated'],
    order: 40,
    menuItems: [{
      id: 'notes-overview',
      labelKey: 'features.notes.overview',
      to: '/notes',
      exact: true,
      audiences: ['authenticated']
    }]
  }],
  policy: {
    owner: noteActions,
    admin: noteActions,
    member: ['read', 'create']
  }
}
```

Use stable, globally unique feature and contribution IDs. `audiences` decide shell visibility; they do not authorize server requests.

## 3. Register the feature

Register from a client plugin owned by the layer:

```ts [layers/notes/app/plugins/notes-feature.ts]
import { notesFeature } from '../../shared/feature'

export default defineNuxtPlugin(() => {
  usePortalFeatures().registerFeature(notesFeature)
})
```

Registration with the same feature ID replaces the previous definition. Production features use that property to re-register capability-filtered menus, badges, and dashboard widgets after loading the active organization’s permissions.

Do not add a Notes entry to the host navigation. The registry is the integration point.

## 4. Add translations and a page

Keep all messages in a collision-safe feature namespace and keep the English and Dutch key trees identical:

```json [layers/notes/i18n/locales/en.json]
{
  "features": {
    "notes": {
      "title": "Notes",
      "overview": "All notes",
      "empty": "No notes yet"
    }
  }
}
```

```json [layers/notes/i18n/locales/nl.json]
{
  "features": {
    "notes": {
      "title": "Notities",
      "overview": "Alle notities",
      "empty": "Nog geen notities"
    }
  }
}
```

Pages, components, and composables inside the layer are discovered like normal Nuxt application files:

```vue [layers/notes/app/pages/notes/index.vue]
<script setup lang="ts">
const { data: notes, status, error, refresh } = await useFetch('/api/notes')
</script>

<template>
  <UPage>
    <UPageHeader :title="$t('features.notes.title')" />
    <UAlert v-if="error" color="error" title="Could not load notes" />
    <div v-else-if="status === 'pending'">Loading…</div>
    <p v-else-if="!notes?.length">{{ $t('features.notes.empty') }}</p>
    <ul v-else>
      <li v-for="note in notes" :key="note.id">{{ note.title }}</li>
    </ul>
    <UButton class="mt-4" color="neutral" variant="outline" @click="refresh()">
      Refresh
    </UButton>
  </UPage>
</template>
```

Localize every visible production string; the literal loading, error, and refresh labels above are kept short only to make the first page easy to follow.

## 5. Protect every server route

Runtime feature code imports portal-core adapters rather than Better Auth, stores, or host database internals:

```ts [layers/notes/server/api/notes/index.get.ts]
import { requireFeatureAccess } from '#portal/server/portal'
import { notesFeature } from '../../../shared/feature'
import { db } from '#portal/server/portal'
import { eq } from 'drizzle-orm'
import { note } from '../../db/schema/notes'

export default defineEventHandler(async (event) => {
  const { organizationId } = await requireFeatureAccess(
    event,
    notesFeature.policy,
    'read'
  )

  return db.select({ id: note.id, title: note.title })
    .from(note)
    .where(eq(note.organizationId, organizationId))
})
```

`requireFeatureAccess` requires a signed-in user, resolves the active organization, checks membership and the policy, and applies the system-administrator bypass. Scope the repository query with the returned `organizationId`.

Never trust an organization ID from query parameters or a request body when the authenticated session already determines the tenant. Apply the same check independently to every create, update, delete, export, attachment, and background-action endpoint.

## 6. Own a PostgreSQL schema

Feature-owned tables and enums belong in a PostgreSQL schema derived from the layer name. Hyphens become underscores, so `service-requests` owns `service_requests`:

```ts [layers/notes/server/db/schema/notes.ts]
import { pgSchema, text, timestamp, index } from 'drizzle-orm/pg-core'
import { organization, user } from '../../../../portal-core/server/db/schema/auth-schema'

export const notesSchema = pgSchema('notes')

export const note = notesSchema.table('note', {
  id: text('id').primaryKey(),
  organizationId: text('organization_id')
    .notNull()
    .references(() => organization.id, { onDelete: 'cascade' }),
  createdById: text('created_by_id')
    .notNull()
    .references(() => user.id, { onDelete: 'restrict' }),
  title: text('title').notNull(),
  createdAt: timestamp('created_at').defaultNow().notNull()
}, table => [
  index('note_organization_id_idx').on(table.organizationId)
])
```

This physical portal-core import is allowed only in Drizzle schema files because Drizzle Kit does not resolve Nuxt aliases. Do not use the same exception in API or application code.

The root Drizzle configuration discovers `layers/*/server/db/schema/**/*.ts` and owns one ordered migration history for the whole application:

```bash [Terminal]
pnpm exec drizzle-kit generate --name=add-notes
pnpm exec drizzle-kit migrate
```

Review the generated SQL. Test it on a disposable PostgreSQL database before committing it, especially when a change renames or removes existing objects.

## 7. Add dashboard contributions only when useful

A dashboard widget needs a stable ID, component, area, size, and order:

```ts
dashboardWidgets: [{
  id: 'notes-recent',
  component: 'NotesDashboardRecent',
  area: 'aside',
  size: 'full',
  order: 20
}]
```

For role- or capability-dependent widgets, import the Vue component in the registration plugin and re-register a filtered definition when the active organization changes. Study the timesheets plugin for capability filtering and service requests for role filtering. Keep authorization in the API even when the widget is hidden.

## 8. Prove the boundary

At minimum, test policy behavior and locale parity inside `layers/notes/test/notes.test.ts`. Add endpoint tests for unauthenticated, unauthorized, allowed, and cross-organization cases; add migration assertions when data safety depends on generated SQL.

Run the project gates:

```bash [Terminal]
pnpm test:features
pnpm eslint layers/portal-core layers/notes
pnpm typecheck
pnpm build
```

Then verify portability rather than assuming it:

1. Build with `layers/notes` enabled.
2. Move it outside `layers/`, restart Nuxt, and build again.
3. Put it in a clean Customer Portal checkout and repeat the checks.
4. Search runtime code for `~/`, `~~/`, `useUserStore`, direct Better Auth use, and host-specific names.
5. Confirm every tenant-owned query includes the active organization.
6. Confirm every feature-owned database object lives in `notes`, not `public`.

Use [service requests](/modules/service-requests) as the compact source reference and [timesheets and invoices](/modules/timesheets-invoices) for multiple modules, dynamic capabilities, approvals, documents, and cross-organization collaboration. When the clean-checkout test passes, continue with [Distribute a feature layer](/contributing/distribute-a-layer).
