# `@nuxt-customer-portal/invoices`

Standalone sales and received invoicing for Nuxt Customer Portal. Add the optional
`@nuxt-customer-portal/invoice-timesheets` layer to create invoices from approved time.

Draft invoice editing includes line descriptions, quantities, units, prices, VAT, and adding or removing lines, with live totals. Creation and editing share a sortable line list: select a line to expand its fields, reorder using the same drag-preview and automatic edge-scrolling pattern as the media library, or focus the handle and use arrow keys, and use Done to collapse it. Only one line's fields are mounted at a time. Adding a line opens it and focuses its description; invalid collapsed lines reopen on submission. VAT rates display percentage signs. Existing line IDs and linked time entries are retained for edited or reordered lines; removing a line releases its linked time entries. Creation from approved time still prevents removing source-linked lines. Issued, paid, and void invoices cannot be edited. Exact tax amounts are preserved unless quantities, prices, or VAT change. Purchase-backed drafts must retain their agreed total, and financial line changes require tax review again. Failed saves retain the editor and its inputs.

The New invoice action links directly to the creation page. Duplicating or crediting an invoice opens the newly created draft directly in edit mode. Normal detail visits remain read-only until Edit is selected. Optional invoice sources load independently of the manual invoice wizard; a source failure shows a warning without blocking free-form creation. Bootstrap and invoice-number failures show an error with a retry action rather than leaving an empty page.

When free-form invoicing is the only available source, the wizard starts with client selection and uses two steps: client and invoice details. Back navigation does not reopen the skipped source selection. If an optional source is available, source selection remains visible and step counts follow the chosen flow.

Set **Default VAT (%)** under **Invoices → Workspace settings → Invoice configuration**. The percentage is validated between 0% and 100%, with up to two decimal places, and saved for the active workspace. It initializes new invoice lines, including lines added while editing a draft; it does not overwrite existing line rates or imported source tax amounts.

Sales invoice details retain the list return URL, including search, filters, sorting, direction, and page. Returning with the invoice's Back link or browser history restores the loaded page window and scroll position after fetching fresh list data. Position snapshots contain only pagination and scroll metadata and are scoped to the current user, organization, and list URL in session storage. Changing collection controls resets the list to page 1 and the top; browser Back/Forward rehydrates those controls from the URL. Links opened directly still return to the default invoice list, and invoices opened from orders retain their order-list return path.

Invoice email status is refreshed on opening an invoice only when an unresolved delivery is due for a check. Delivered, opened, clicked, bounced, failed, suppressed and complained messages are excluded from automatic checks. Unresolved messages are checked at most every five minutes during the first day, hourly after one day, and daily after a week. Failed lookup attempts observe the same cooldown while preserving the last known status. Concurrent requests claim each attempt in the database before contacting the provider.

Manual refresh can check resolved deliveries for later engagement or complaints, with a one-minute cooldown per message. These events are not updated automatically after delivery; receiving them continuously would require a Resend webhook integration.

## Recurring invoices

Use **Invoices → Recurring invoices** to create a template with a client, optional billing contact, invoice lines, payment term, recurrence period, first invoice date and optional inclusive last invoice date. Daily, weekly, monthly, quarterly and yearly schedules are supported. A blank end date repeats indefinitely. The first invoice date anchors the recurrence: January 31 repeats on February 28/29 and then March 31, without date drift.

The Nitro task `invoices:recurring` runs every minute on deployments supporting scheduled tasks. Otherwise configure the deployment scheduler to invoke this task every minute. Apply package migrations before deploying the task. A draft is created on or after midnight in the schedule's explicit IANA timezone; it is **never automatically issued, emailed or marked paid**. Drafts use the planned date as the invoice date and add the configured calendar-day payment term for their due date. Sender/recipient details are resolved when each draft is created; invoice numbering uses the existing organization sequence.

Use `{{period}}`, `{{month}}`, `{{year}}`, `{{week}}`, `{{week_year}}`, `{{period_start}}` and `{{period_end}}` in the description, notes and line descriptions. The editor previews the next occurrence. Month names use the selected English/Dutch language. For example, `Hosting {{period}}` becomes `Hosting December 2026`; a weekly schedule can render `Week 52 2026`. Week and week-year use ISO 8601 (January 1, 2027 belongs to week 53 of 2026). Period start/end are ISO dates covering the planned occurrence through the day before the next occurrence; the last invoice date limits invoice creation, not the service period. Quarterly `{{period}}` uses the calendar quarter containing the invoice date.

For billing in arrears, use `{{previous_period}}`, `{{previous_month}}`, `{{previous_year}}`, `{{previous_week}}`, `{{previous_week_year}}`, `{{previous_period_start}}` and `{{previous_period_end}}`. A monthly invoice dated November 1, 2026 renders `Hosting {{previous_period}}` as `Hosting October 2026`, with service dates October 1–31. The previous period follows the same recurrence anchor and ends the day before the planned invoice date, including on the first occurrence. Month-end anchors, leap years and ISO week years apply to these placeholders too. Invoice and due dates are unchanged; current and previous placeholders can be mixed.

Disable a schedule to pause it. Re-enabling, selecting a past first invoice date, or recovering from downtime catches up all missed occurrences in chronological order in the same run, up to 50 schedules per run. Future dates are never generated early. Each draft and cursor advancement is committed atomically; a failure stops that schedule at the failed date while retaining earlier drafts for safe retry. Transactional row locking and a unique schedule/date constraint prevent duplicate drafts on overlapping runs or retries. Deleting a generated draft does not rewind the schedule. Disabled invoicing suspends generation. Errors are displayed on the schedule and retried automatically; fix the sender, client/contact or template details as needed. Existing drafts are unchanged by template edits. After the first draft, the start date, recurrence period and timezone cannot be changed; pause the old schedule and create a new one instead. Extending an end date resumes from the next ungenerated occurrence.

Run the calendar/template tests with `node --import tsx --test packages/invoices/test/recurring-invoice.test.ts`. For PostgreSQL integration coverage, create an empty disposable database named `codex_recurring_invoices_test_<suffix>`, set `RECURRING_INVOICES_TEST_DATABASE_URL` to its connection URL, and run `node --import tsx --test packages/invoices/test/recurring-invoice-database.test.ts`. This test applies migrations and seeds fixtures; never use a development or production database. Drop the disposable database afterwards.
